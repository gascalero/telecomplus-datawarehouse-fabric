-- Quality Check Validation Description:
--
-- The quality check validation process followed four standard rules [1]:
-- *   **Rule # 1: Check Integrity of Business Key (for DIM tables)** [1]
-- *   **Rule # 2: Check Uniqueness of dimension attributes (for DIM tables)** [1]
-- *   **Rule # 3: Check Integrity of Fact table's PK (for FACT tables)** [1]
-- *   **Rule # 4: Check relationship of foreign key in Fact table (for FACT tables)** [1]
--
-- A 'log_quality_checks' table was created in the staging area to record any quality issues [1, 2].
-- According to the sources, **no errors were detected** after running the validation pipeline [1, 2].
--
-- Dimension Tables Quality Checks:
--
-- *   **Rule # 1: Check Integrity of Business Key (for DIM tables)** - This check ensures that the **business keys** (e.g., `bk_customer` in `dim_customer`, `bk_agent` in `dim_agent`, `bk_channel` in `dim_channel`, `bk_plan` in `dim_plan`, and `bk_reason` in `dim_reason`) in each dimension table are **not null** and maintain their integrity. Business keys are the natural keys from the source systems that uniquely identify each dimension member.
--
-- *   **Rule # 2: Check Uniqueness of dimension attributes (for DIM tables)** - This rule focuses on ensuring the **uniqueness of key attributes** within each dimension table. For example, it might check if there are duplicate `agent_name` values in the `dim_agent` table when they should be unique, or if `channel_platform` values in `dim_channel` are consistent.
--
-- Fact Tables Quality Checks:
--
-- *   **Rule # 3: Check Integrity of Fact table's PK (for FACT tables)** - This check pertains to the **primary keys** of the fact tables (`fact_customer_interactions_cases` and `fact_signups_record`). Fact tables typically have **composite primary keys consisting of foreign keys referencing the dimension tables**. This rule would ensure that these **foreign key combinations are not null** and maintain the integrity of the fact table's primary key.
--
-- *   **Rule # 4: Check relationship of foreign key in Fact table (for FACT tables)** - This is crucial for **referential integrity**. It verifies that the **foreign keys** in the fact tables (e.g., `fk_date`, `fk_agent`, `fk_channel`, `fk_customer`, `fk_reason` in `fact_customer_interactions_cases`; `fk_signup_date`, `fk_termination_date`, `fk_customer`, `fk_plan` in `fact_signups_record`) correctly reference valid **surrogate keys** (`sk_date`, `sk_customer`, `sk_agent`, `sk_channel`, `sk_plan`, `sk_reason`) in their corresponding dimension tables. This ensures that **every fact record is associated with valid dimension members**.


-- SQL RULE 1 ON STG DIM CHANNEL

INSERT INTO STG_TELECOMPLUS_SUBSCRIPTIONS.dbo.log_quality_check
SELECT 1 AS ID_CHECK,
	'Staging Area' AS ETL_PHASE,
	'stg_dim_channel' AS ETL_TABLE,
	'check integrity of BK' AS ETL_CHECKTYPE,
	'number of rows with repeated BK: ' + str(count(row_count)) AS DESCRIPTION_RESULT,
	CASE 
		WHEN count(row_count) > 0
			THEN 'FAIL'
		ELSE 'OK'
		END AS ETL_RESULT
FROM (
	SELECT count(*) AS row_count
	FROM STG_TELECOMPLUS_SUBSCRIPTIONS.dbo.stg_dim_channel
	GROUP BY bk_channel
	HAVING count(*) > 1
	) q;
